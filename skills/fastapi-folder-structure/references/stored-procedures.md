# Stored-procedure APIs

Use only when SP mode is required. Map each data-backed API operation to its own approved public API-entry SP; each repository operation executes exactly one public entry call. No public entry is shared across distinct API operations.

- **Entry boundary:** the entry SP performs all persistence needed by its operation, including supporting lookups, database-backed authentication/authorization checks, and counts. Reuse private procedures/functions/views/helpers internally. HTTP-facing repositories must never call private routines, chain public entries, or fall back to direct tables, ORM queries, or ad-hoc SQL. Migration/admin commands remain separate.
- **Input contract:** identify the owning API operation, fixed schema-qualified entry name, parameter names/directions/order, database and application types, nullability/defaults, and filter/sort/pagination inputs. Separate trusted actor/tenant context from client-writable fields. Inspect definitions or obtain the deployment owner's contract; do not guess externally maintained signatures.
- **Output contract:** document result-set count/order, columns/types/nullability, cardinality and empty/not-found behavior, output parameters, pagination/count metadata, and stable business failure codes. Keep typed adapters and public schemas aligned with actual driver results; compile-time types alone do not verify SQL outputs. Return codes are not automatically HTTP statuses; map known failures centrally without exposing driver errors.
- **Safe execution:** bind values using the installed driver's procedure protocol. Never select routine names or SQL fragments from request data, or substitute a directly callable function for the approved entry SP. Parameterize/allowlist dynamic SQL inside private routines too. See [OWASP guidance](https://cheatsheetseries.owasp.org/cheatsheets/SQL_Injection_Prevention_Cheat_Sheet.html).
- **Scope and transactions:** entry/private SQL enforces trusted row scope, referenced-ID access, persisted invariants, and database pagination/counting. Choose one transaction owner. An application-owned transaction wraps only the entry call; any internal helper composition must preserve the operation's atomicity contract. Inspect implicit driver transactions before invoking self-committing SPs; observe engine-specific rules such as [PostgreSQL CALL restrictions](https://www.postgresql.org/docs/current/sql-call.html). A transport failure does not prove rollback. Do not retry the entry call within an API operation; client retries require explicit idempotency safety.
- **Deployment:** version definitions/grants through the existing database deployment system, not competing copies or request-time installation. Deploy compatible input/output contracts before their callers. Use least-privilege runtime credentials and release owned resources on failure.

**Verify:** against an isolated database, check distinct operation-to-entry mappings, exactly one entry invocation per repository operation, no extra persistence calls from service orchestration, no public-entry reuse or repository calls to private helpers/direct queries, input/output contracts, tenant isolation, empty/multi-result cases, pagination, and atomicity/failures. Mocks alone cannot verify deployed SQL.

**FastAPI:** inject the driver resource into repositories; preserve synchronous/asynchronous execution and cleanup rules. Feature result types need no ORM entities or identity-map session when the driver does not require them.
